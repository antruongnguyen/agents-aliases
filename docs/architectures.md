# Architecture

How `agents-aliases` is structured and why.

## Design principle: pure core, thin shell

Everything that reasons about the project is a **pure, testable function** over plain data. Only two places touch reality:

1. `detect.ts` — reads the filesystem into a snapshot.
2. `applyPlan()` / `sync` / `check` — act on it.

The interactive wizard is a thin `@clack/prompts` layer that merely *produces* a `Choices` object. The same `Choices` can come from flags (`--yes --agents claude`). All business logic lives below the prompt layer and runs identically in CI, tests, and TTYs.

## Module map

```
src/
├── cli.ts              parseArgs + dispatch; maps exit codes 0/1/2
├── presets.ts          THE tool registry: concerns, paths, adapters,
│                       canonical order, agent shortcuts, scaffold stub
├── detect.ts           scan(cwd) -> Detection (filesystem snapshot)
├── engine/
│   ├── planner.ts      plan(detection, choices) -> Plan   (pure, async)
│   │                   applyPlan(detection, plan, dryRun) (the only writer)
│   ├── symlink.ts      relativeLinkTarget / createSymlink /
│   │                   replaceWithSymlink (atomic tmp+rename swap)
│   └── rules.ts        frontmatter split/serialize, generateAdapter,
│                       marker make/parse, targetFileName mapping
├── commands/
│   ├── init.ts         wizard-or-defaults -> preview -> confirm -> apply
│   ├── status.ts       render Detection
│   ├── sync.ts         repair pass (links + generated files)
│   └── check.ts        verification pass (CI gate)
└── ui/prompts.ts       @clack/prompts wrapper; Choices factory
```

## Core type contracts

```ts
// filesystem snapshot — no behavior, just facts
interface Detection {
  root: string;
  concerns: Record<ConcernKind, {
    states: Map<presetId, { relPath, type, linkText? }>; // file|dir|symlink-*|broken|missing
    sources: presetId[];      // real files/dirs = canonical candidates
    links: presetId[];        // working symlinks
    brokenLinks: presetId[];
  }>;
  fileHashes: Map<path, sha256-16>;     // instruction files
  dirSignatures: Map<path, treeHash>;   // skills/rules/plugins dirs
  generatedFiles: { dirPresetId, fileName, sourceRelPath }[];  // marker hits
  isGitRepo: boolean;
  dirtyPaths: Set<string>;              // git status --porcelain
}

// intent — from wizard or from flags
type Choices = Record<ConcernKind, {
  enabled: boolean;
  canonicalId: string | null;
  targetIds: string[];
}>;

// diff between desired and actual
interface Plan {
  actions: Action[];      // scaffold | symlink{create|replace|repair} | generate{create|regenerate}
  noopCount: number;      // already-correct wiring
  warnings: string[];     // applied anyway / need attention
  blocked: string[];      // refused for safety; never silently skipped
}
```

Pipeline per command:

```
detect() ──► Choices (wizard | defaultChoices) ──► plan() ──► applyPlan()
    │                                                        or check/sync
    └───────────────────── status renders Detection alone ──┘
```

## Filesystem-as-state

There is deliberately **no config file and no lock/state file**. Intent is inferred on every run:

- A symlink at a preset path *is* the record of "this tool is wired to X".
- The marker comment inside generated files records provenance (`Source: <path>`), so any generated file can be re-derived and compared without external bookkeeping.
- Consequence: `check`/`sync` work in any clone without setup, and "uninstall" is `git clean` of symlinks. Cost: the tool can only verify wiring that exists on disk — it cannot know you *wanted* an alias that was never created. Creating new wiring is therefore the wizard's job; `sync` only repairs.

## Why rules are generated instead of linked

Cursor MDC files require `description`/`globs`/`alwaysApply`; Copilot scoped instructions require `applyTo`; Windsurf uses `trigger`. A raw symlink would expose one format to tools expecting another, so each target gets a deterministic adapter: marker line + mapped frontmatter + canonical body. Determinism (`generateAdapter` is pure) replaces lockfiles: drift = regenerated bytes differ from disk bytes.

## Symlink mechanics

- Links are always **relative** (`../AGENTS.md`), computed via `path.relative(dirname(target), source)` — clones and moved checkouts keep working.
- Replacement is atomic-ish: create temp link → remove old → rename temp into place, so a crash cannot leave a path both missing and half-written.
- Windows `EPERM`/`EACCES` on creation is converted to `WindowsSymlinkError` with Developer-Mode guidance rather than a raw stack trace.

## Safety gates (planner-level)

Destructive actions are gated where they're *planned*, not where they're executed:

- differing-duplicate replacement requires `isGitRepo && !dirtyPaths.has(path)` — otherwise the action becomes a `blocked` entry with an explanation;
- non-instruction concerns (skills/plugins) are never auto-replaced when content differs — merge conflicts must be human-resolved;
- foreign rule files block the whole target dir to avoid mixed generated/authored states.

Because gates live in `plan()`, every consumer (wizard preview, `--yes`, dry-run) inherits them automatically.

## Testing strategy

58 tests across 8 files:

| Layer | Approach |
| --- | --- |
| `presets`, `rules`, `symlink` | Unit tests incl. link-target math (`root→root`, `nested→root`, `nested→nested`) |
| `detect` | Fixture trees in `os.tmpdir()`: real/symlink/broken/generated-marker classification, hash equality |
| `planner` | Scenario matrix: clean adopt, identical/differing duplicates × git/no-git × clean/dirty, noop vs repair, rules generation/naming/drift/foreign-block, dry-run immutability |
| `choices` | Default-choice semantics incl. `--agents` shortcut filtering and scaffold fallback |
| `wizard` | `vi.mock("@clack/prompts")`: enter-through-everything produces all-agent wiring; declined concern respected |
| CLI smoke | Spawns built `dist/cli.js` against fixtures: `--help/--version`, unknown-command exit 2, full non-interactive wire, dry-run leaves FS untouched, `check` failing cases, `sync` refresh + unfixable reporting |

Interactive-only code paths are kept minimal so coverage doesn't depend on a TTY; `pnpm test` builds first because smoke tests execute the real bundle.

## Build & release

- **tsdown** bundles `src/cli.ts` → single-file ESM `dist/cli.js` (~39 kB) with shebang preserved.
- `package.json` exposes `bin.agents-aliases`; `files: ["dist"]` keeps the tarball at ~13 kB packed; the `packageManager` field pins pnpm for CI and enables setup-node's automatic cache.
- Two GitHub Actions workflows:
  - **CI** (`ci.yml`, push/PR): a `verify` job (lint → typecheck → build → `npm pack --dry-run`) plus a `test` matrix over Ubuntu/macOS/Windows × Node 20/24.
  - **Release** (`release.yml`, tag `v*`): verify → build → `pnpm publish --access public` (using the `NPM_TOKEN` secret) → GitHub release with the packed tarball attached and generated notes.
- Uses current action majors: `actions/checkout@v7`, `actions/setup-node@v7`, `pnpm/action-setup@v4`, `softprops/action-gh-release@v2`.
