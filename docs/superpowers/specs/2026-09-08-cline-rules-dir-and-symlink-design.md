# Cline rules: `.cline/rules` location + same-format symlink wiring

**Date:** 2026-09-08
**Status:** Approved design, pending spec review

## Problem

The upstream Cline docs now describe a unified `.cline/` project-config directory
(`.cline/rules`, `.cline/skills`, `.cline/hooks`, …). This tool currently wires Cline
rules to the legacy `.clinerules/` directory and treats the whole `rules` concern as
"generate a per-file adapter for every target". Two consequences:

1. Cline rules live at `.clinerules`, inconsistent with the `.cline/skills` we already
   wire and with Cline's own documented layout.
2. When Claude is canonical and Cline is a target, we *copy* Claude's rules into Cline's
   dir as generated adapters — even though `rules-claude` and `rules-cline` use the
   **same** adapter format (`claude`: plain `.md` with `paths:` frontmatter). The copy is
   redundant; a symlink is cleaner and keeps the two in lockstep.

## Goals

1. Move the Cline rules preset from `.clinerules` to `.cline/rules`.
2. When a rules target shares the canonical's adapter format, wire it as a **relative
   directory symlink** (the mechanism skills/plugins/instructions already use) instead of
   generating per-file copies. This makes Claude↔Cline rules a symlink.
3. Migrate an existing `.clinerules/` directory to `.cline/rules/` automatically, gated by
   the same git-safety rule as other destructive operations, and tell the user why.
4. Update all docs (README, `docs/features.md`, `docs/architectures.md`) to match, and
   correct the stale claim that Cline "is not wired for instructions" — Cline reads
   `AGENTS.md` natively, so no instruction file is needed (same as Codex/Cursor).

## Non-goals

- Global `~/.cline/` config, `~/Documents/Cline/` search paths, env vars
  (`CLINE_DATA_DIR`, `CLINE_COMMAND_PERMISSIONS`, …). This tool wires **project-level**
  files only; the filesystem is the single source of truth. Out of scope.
- Adding a dedicated Cline *instructions* file. Cline reads `AGENTS.md` natively; wiring a
  separate file would be redundant.
- Continuing to support `.clinerules` as a live wiring target after migration.

## Current architecture (recap)

`plan()` (`src/engine/planner.ts`) routes each concern to one of two mechanisms:

- `planAliasConcern` — instructions, skills, plugins → **relative symlinks**.
- `planRulesConcern` — rules → **generated per-file adapters** (`generateAdapter`), one
  output file per canonical rule file, each carrying the
  `<!-- GENERATED by agents-aliases. Source: … -->` marker.

`presets.ts` is the only place with tool knowledge. `rules-claude` and `rules-cline` both
declare `adapter: "claude"`; Cursor/Windsurf/Copilot declare distinct formats.

## Design

### 1. Preset change (`src/presets.ts`)

- Change `rules-cline.path` from `.clinerules` → `.cline/rules`. Keep `adapter: "claude"`.
- No new preset for `.clinerules`; it is recognized only by the migration step (below),
  not by `PRESETS`. The `cline` shortcut and picker entry are unchanged (they already map
  to `skills-cline` + `rules-cline`).

### 2. Same-format targets wire as a directory symlink

Introduce the rule: **a rules target whose `adapter` equals the canonical's `adapter`
is wired as a relative directory symlink to the canonical dir, not as generated
adapters.** Targets with a different adapter keep generating per-file adapters unchanged.

Implementation in `planRulesConcern` (`src/engine/planner.ts`):

- Compute `canonical.adapter`. Partition `choice.targetIds` into:
  - **link targets** — `target.adapter === canonical.adapter`
  - **generate targets** — everything else
- For **link targets**, emit the same `{ kind: "symlink", … }` actions the alias path
  produces, reusing the existing `PathState` switch semantics:
  - `missing`/`undefined` → `symlink create`
  - `broken-symlink` → `symlink repair`
  - `symlink-*` pointing at canonical → noop; elsewhere → `symlink repair`
  - real `dir` whose `dirSignature` matches canonical → `symlink replace` (safe: content
    identical); real `dir` that differs → `conflict` (git-safety gated in `resolveConflicts`,
    exactly like the alias path) rather than silent overwrite.
  - A **foreign/unmarked** file rule still applies: if the target dir holds authored
    (non-generated) rule files that differ from canonical, it is a conflict, not a link.
- **generate targets** run the existing per-file `compareGenerated` loop untouched.

To avoid duplicating the alias switch logic, extract the per-target state→action decision
in `planAliasConcern` into a small shared helper (e.g. `planDirSymlinkTarget(detection,
target, canonical, plan)`) and call it from both `planAliasConcern` and the link-target
branch of `planRulesConcern`. This keeps one code path for "wire dir B as a symlink to dir
A" and preserves the existing safety gates for free.

**Determinism note:** the byte-stability guarantees in `test/rules.test.ts` concern
`generateAdapter` output only. Link targets never call `generateAdapter`, so those tests
are unaffected. New behavior is covered by new planner tests.

**Verbatim vs normalized:** a symlinked `.cline/rules` exposes Claude's rule files exactly
as authored (including any extra frontmatter keys and no generated marker). This is correct
— Cline reads `paths:` and ignores unknown keys, same as Claude — and is the intended
semantics: "Cline sees exactly Claude's rules."

### 3. `.clinerules` → `.cline/rules` migration

A migration runs when planning the rules concern and Cline is among the enabled presets
(canonical or target):

- **`.clinerules` exists, `.cline/rules` does not** → plan a migration action that moves
  every rule file from `.clinerules/` into `.cline/rules/`, then removes the now-empty
  `.clinerules/`. Gated by git-safety: only performed when `isGitRepo && no dirty path
  under .clinerules`; otherwise it becomes a `blocked` entry explaining the git-safety
  requirement (never a silent move). The summary prints a one-line reason:
  *"Cline moved project rules from `.clinerules` to `.cline/rules`; the old location is
  deprecated."*
- **Both `.clinerules` and `.cline/rules` exist** → do not move. Emit a `warning`:
  *"Both `.clinerules` and `.cline/rules` exist; `.clinerules` is deprecated — merge it into
  `.cline/rules` and delete it."* Wiring proceeds against `.cline/rules`.
- **Only `.cline/rules` (or neither)** → no migration; normal wiring.

The migration is a new `Action` variant (e.g. `{ kind: "migrate"; op: "move"; fromDir;
toDir; files }`) planned in `plan()` and executed by the sole writer `applyPlan()`
(`src/engine/apply.ts`). It is surfaced in the setup summary (`src/ui/summary.ts`) as its
own block so the user sees what moved and why.

Because migration produces the `.cline/rules` dir that step 2 then wires, ordering in
`plan()` matters: detect `.clinerules`, plan the migration first, then plan the rules
targets treating `.cline/rules` as present.

### 4. Documentation updates

- **README.md** — supported-tools table, wiring table, layout tree, and the intro
  paragraph: replace `.clinerules` with `.cline/rules`; note Claude↔Cline rules are a
  symlink (same format), other tools remain adapters.
- **docs/features.md** — rules row, the preset table (`rules-cline` path + "dir symlink
  when same format"), and the instructions note: correct
  *"Cline … is not wired for instructions here"* to state Cline reads `AGENTS.md`
  natively (like Codex/Cursor), so it needs no instruction file; it is wired for skills
  and rules.
- **docs/architectures.md** — the two-mechanism description: rules are generated adapters
  **except** when a target shares the canonical's format, in which case the dir is
  symlinked; document the `.clinerules → .cline/rules` migration as a planned, git-gated
  action.
- The **detection-matrix region** in `docs/features.md` (between the `BEGIN/END GENERATED:
  detection-matrix` markers) is derived from `PRESETS` and verified by `test/docs.test.ts`.
  Regenerate that region from `renderDetectionMatrix` (do not hand-edit it) and paste the
  block the test prints. All other doc prose in README/features.md/architectures.md is
  hand-written and edited directly.

## Testing

1. **Preset** (`test/presets.test.ts`): `rules-cline` resolves to `.cline/rules`; `cline`
   shortcut still expands to `skills-cline` + `rules-cline`.
2. **Same-format symlink** (`test/planner.test.ts`): Claude canonical + Cline target →
   `symlink create .cline/rules → .claude/rules` (relative), **not** a `generate` action.
   Cursor/Windsurf/Copilot targets in the same run still `generate`. Reverse (Cline
   canonical + Claude target) → `symlink` to `.cline/rules`. Existing matching-symlink →
   noop; differing real dir → conflict (git-gated).
3. **Migration** (`test/planner.test.ts` + apply/smoke): `.clinerules` present, `.cline/rules`
   absent, clean repo → migrate action moves files and removes `.clinerules`; dirty/non-repo
   → blocked with reason. Both dirs present → warning, no move. `applyPlan` performs the move
   atomically and idempotently (re-run is a noop).
4. **Determinism** (`test/rules.test.ts`): unchanged and still green (adapter output
   untouched).
5. **Docs matrix** (`test/docs.test.ts`): the regenerated detection-matrix region in
   `docs/features.md` matches `renderDetectionMatrix` output.

## Risks / edge cases

- **Extract-helper refactor** touches `planAliasConcern`, which has no direct test
  coverage per the blast-radius report. Mitigate by asserting existing instructions/skills
  symlink behavior is unchanged (add a characterization test if none covers it) before
  refactoring.
- **Migration + symlink interaction:** after migrating `.clinerules` into `.cline/rules`,
  if Cline is a *target* of a Claude canonical, the freshly-created `.cline/rules` is a
  real dir with content identical to `.claude/rules` → `symlink replace` (safe). If it
  differs from Claude's, it is a conflict, not an overwrite. Both paths are git-gated.
- **Only-Cline runs (no Claude):** with Cline as canonical and no other rules target, the
  concern is a noop beyond migration — acceptable.
